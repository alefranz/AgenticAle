Slide 1: Title & Introduction

  • Welcome everyone. Most of us use GitHub Copilot or coding agents every day now, and for small edits or quick questions, a normal chat session is great.
  • But as soon as you hand an agent a real engineering task—something that touches multiple files, requires investigating dependencies, and needs to end in a solid PR—raw single-thread chat starts showing cracks.

Section 1 • The Problem

Why Single-Context AI Coding Breaks Down

Four structural failure modes in long-running single-thread chat sessions

1 Context Rot & Anchoring

Failed grep searches, half-read files, and dead-end edits accumulate in the prompt window.

  • Later turns pay the attention & token tax of earlier mistakes.
  • The agent anchors to outdated assumptions and hallucinated paths.

2 Self-Review Bias

Asking the same session "Did you miss anything?" rarely catches bugs.

  • Shares the exact blind spots and reasoning chain that created the bug.
  • Rubber-stamps flawed code because its own rationale is right there in context.

3 One-Size-Fits-All Model Selection

Locked to a single model choice across completely different task phases.

  • Using a heavy reasoning model for basic file search wastes quota & time.
  • Leaving a fast model on for tricky edge cases causes subtle regressions.

4 The Manual Babysitting Tax

Engineers end up manually managing the agent's context hygiene.

  • Manually resetting chat windows, copy-pasting handoff summaries.
  • Switching models mid-stream and re-explaining repo requirements.

Slide 2: Why Single-Context AI Coding Breaks Down

  • Let's name the four failure modes we've all experienced:
  • First, context rot: twenty minutes into a session, 70% of your context window is dead stack traces and files that turned out to be irrelevant. The model gets anchored to its initial wrong assumption.
  • Second, self-review bias: when an agent writes code and you ask it in the same thread to review its work, it almost always rubber-stamps it because the reasoning that produced the bug is still sitting right there in context.
  • Third, wrong model for the job: you either burn expensive reasoning quota on simple file discovery, or you leave a fast model on and watch it struggle on a tricky architectural fix.
  • Fourth, cognitive overhead: you can manually open new chats, paste context packets, and switch models yourself—but you shouldn't have to.

⚖️ A Conscious Compromise by Design

Orchestration overhead: Spawning subagents adds slight latency—not meant for a 1-line typo fix.
The payoff: Automatically manages context isolation, per-role model configuration, and independent review gates for 90% of real engineering work.

Slide 3: Enter /work — Opinionated Subagent Orchestration

  • This is where the /work skill comes in. Its philosophy is simple: automate good agentic hygiene so you don't have to think about it.
  • When you run /work, your main chat session stops writing code directly. Instead, it becomes the Coordinator.
  • The Coordinator inspects the repo state, builds a focused Task Packet (just the facts, scope, and acceptance criteria—never the noisy conversation history), and spawns a fresh subagent for each phase.
  • Yes, there is a deliberate trade-off: spawning subagents adds a bit of latency compared to a single-turn inline edit. That's why /work is explicit-only. You use normal chat for quick questions, and /work when you want a task taken cleanly from prompt to reviewed code or PR.
Section 2 • Core Deep Dive

Fresh Context per Round & The Independent Review Gate

Eliminating context pollution and blind spots through strict round contracts

📦 Task Packets (rounds.md)

Fresh context injected per round; zero history bleed.

  • Strict Child Inputs: Target outcome, exact file scope, repository conventions, and verification commands.
  • Ephemeral Context: The 15 files and 8 test runs inspected during coding disappear when the worker finishes.
  • Structured Return: Worker returns only a concise summary card (keeping the Coordinator context tiny).
  • Repeatable State: Coordinator remains lean across 5, 10, or 20 rounds without degrading.

🛡️ Zero-Trust Independent Review

An unbiased second pair of eyes on disk reality.

  • Blank-Slate Reviewer: Spawns without knowing the worker's struggles, internal debates, or rationalizations.
  • Claims are Unverified: Instructed to distrust worker claims; directly inspects the git diff and untracked files against acceptance criteria.
  • Stable Finding IDs: Issues are flagged with stable IDs (ISSUE-1, ISSUE-2).
  • Verification Loop: Fix rounds address findings; re-review verifies each ID as fixed, still open, or regressed.

Slide 4: Fresh Context per Round & The Independent Review Gate

  • Let's look at why fresh context matters most at the Review Gate.
  • When the implement subagent finishes, it returns a short summary of what it changed and what tests it ran. All the 15 files it read along the way stay in its disposable context and disappear.
  • Next, the Coordinator spins up a brand-new review subagent. Crucially, rounds.md instructs the reviewer to treat the worker's claims as unverified. The reviewer doesn't care that the worker struggled for 10 minutes on a regex—it only sees the original user goal and the actual diff on disk.
  • If the reviewer finds a blocking issue, a fix subagent is dispatched, followed by a re-review that tracks every finding by ID until the gate is clean.

📝 Customizable via Plain Markdown

Slide 5: Right Model for the Job — Per-Role Model Configuration

  • Alongside fresh context, /work solves model selection per role: each of the seven roles — explore, implement, implement-hard, fix, review, deep-review, consult — gets its own model, and where the host supports it, its own reasoning effort.
  • On OpenCode, --models PATH|PRESET sets the model configuration at install time: a flat per-role config — a JSON file or a bundled preset like openai — is baked into the seven generated agent profiles; --no-model inherits the session model.
  • On the other hosts (Copilot, Codex, Antigravity), the configuration is one optional preference file, .agenticale/preferences.md, with direct role assignments like - review: openai/gpt-6.1-sol, xhigh — a project file wins over the personal one, and nothing else is interpreted.
  • For named setups, a leading --profile NAME selects preferences.NAME.md instead of preferences.md, at .agenticale in the project or under ~/.agenticale — a missing file is a concise, actionable error, never a silent fallback.
  • When a task or review finding needs concurrency, subtle state, security, or difficult contract reasoning, /work runs the implement or fix contract on the implement-hard role, which you can point at your strongest model.
Section 2 • Core Deep Dive

From Prompt to High-Confidence PR

Automating the path from prompt to reviewed pull request with power flags

Flag /work --pr <task>

Full-lifecycle automated delivery to GitHub / remote:

  • Implementation → local verification → independent review → fix loop.
  • Coherent git commit formatting → branch push → creates or updates PR.
  • Supports --pr=<PR-URL> to address review comments directly.

Flag /work --consult <task>

Think before you code with high-reasoning models:

  • Dispatches a read-only consult subagent on its configured model before coding.
  • Challenges requirements framing and surfaces hidden edge cases.
  • Asks only the questions that genuinely require human judgment.

Flag /work --outcome <metric>

Preventing agents from moving the goalposts:

  • Pre-registers baseline metrics & acceptance cards (e.g. "speed up export by 20%").
  • Candidate implementations must prove measurable improvement against baseline.
  • Worker cannot declare victory without meeting the explicit benchmark.

Pattern Sequential Decomposition

Handling large multi-step initiatives cleanly:

  • Slices complex initiatives into small, verifiable milestone steps.
  • Completes, tests, and independently reviews one slice at a time.
  • Prevents runaway edits across dozens of interrelated files.

Slide 6: From Prompt to High-Confidence PR (/work --pr & Power Flags)

  • How does this feel in practice? With /work --pr, you can hand it a bug or feature, and by the time it opens or updates the pull request, the code has already survived local checks and at least one round of independent review.
  • There are also two really useful opt-in flags:
  • --consult dispatches a deep-thinking consultant before a single line of code is written to challenge the requirements and surface trade-offs.
  • --outcome is for measurable targets like latency or bundle size: it pins the baseline metric upfront in an Outcome Card so the agent can't cheat or move the goalposts when evaluating candidates.
Section 3 • Supporting Skills

Guardrail Skills: source-code-lookup & PR Descriptions

Guarding against common model bad habits when dealing with external code and PR text

The Common Trap: When a bug crosses into an internal NuGet/npm package, microservice, or message schema, unguided agents start guessing behavior, hallucinating API contracts, or running decompilers on compiled binaries in cache folders.

🔍 source-code-lookup

Navigating external repos cleanly & accurately.

  • Follows Lockfiles & Schemas: Traces exact package names, versions, and repository endpoints.
  • Local Checkout or Clean Clone: Searches ~/dev / SOURCE_ROOT or clones into canonical paths.
  • Exact Version Pinning: Uses git show <tag/commit> without checking out or dirtying working branches.
  • Isolated Subagent: Runs inside a disposable explore round—2,000 lines of external source never pollute the coder's context!

📝 pull-request-description

High-signal human PR bodies over robotic summaries.

  • No Diff Recaps: Eliminates robotic file lists (*"Modified foo.ts and updated unit tests"*).
  • Intent & Context: Clearly articulates why the change exists and what business problem it solves.
  • Reviewer-Relevant Risks: Highlights operational risks, database migrations, and breaking changes.
  • Non-Obvious Validation: Documents edge cases tested that automated CI cannot cover.

Slide 7: Supporting Skills — Guardrails Against AI Bad Habits

  • Workflow orchestration is only half the story; we also need guardrails for common model bad habits.
  • My favorite example is source-code-lookup. We've all seen what happens when an agent hits a mysterious behavior in an external package or another service: it starts guessing, or worse, runs a decompiler on a compiled package in node_modules or .nuget.
  • With source-code-lookup, the agent checks lockfiles or service configs to find the exact repository and version, looks in your local ~/dev folder (or clones it cleanly), and uses git show at the exact commit matching the deployed version. Even better, /work delegates heavy external lookups to an explore subagent, so reading 2,000 lines of another service only returns a 5-line factual answer to your worker.
  • Similarly, pull-request-description stops agents from writing useless PR bodies like "Updated foo.ts and ran tests", focusing instead on intent, rollout risks, and non-obvious validation.
Section 4 • Ecosystem & Strategy

"Why Not Just Use GitHub Copilot Fusion?"

Understanding the difference between turn routing and architectural workflow boundaries

⚡ When Copilot Fusion Wins (The Sweet Spot)

Zero-ceremony interactive coding, quick questions, inline iterations, pair-programming in the flow, and automatic turn-by-turn model switching.

🛡️ Why AgenticAle /work Still Matters

1. Structural Boundaries

Fusion switches models within a single noisy thread. /work enforces hard context isolation between the coder and an independent reviewer.

2. Explicit Profile Control

Pin exact models and reasoning effort per role across your team (e.g. keeping review on strict high-reasoning models regardless of turn).

3. "Glass Box" Narration

Before every round, the Coordinator narrates: what was learned, what comes next, and why. A powerful learning tool for agentic engineering intuition.

Slide 8: "Why Not Just Use GitHub Copilot Fusion?"

  • Since we use GitHub Copilot, a natural question is: "Why not just use Copilot Fusion, which already routes between models automatically?"
  • And the honest answer is: for everyday interactive back-and-forth, you should! Fusion is great when you're in the driver's seat iterating turn by turn.
  • Where /work shines is two things:
  • First, workflow control: Fusion switches models inside your conversation, whereas /work enforces fresh context isolation between the coder and the reviewer.
  • Second, visibility and learning: /work has a built-in narration contract. Before every subagent dispatch, the Coordinator writes a concise paragraph explaining what the last agent found, what round is running next, and why. Even when your IDE collapses subagent tool calls, you get a crystal-clear narrative of how an agentic system reasons, decomposes slices, and catches its own mistakes. It's one of the best ways to build intuition for agentic engineering.
Section 4 • Ecosystem & Strategy

Shared Skills vs. Every Engineer/Org Forking Their Own

Avoid reinventing workflow plumbing; standardize the core and customize the edges

⚠️ The Forking Plumbing Trap

"Let's just write our own custom review prompt!"

Orchestration edge cases are surprisingly treacherous to maintain:

  • Preventing infinite worker ↔ reviewer ping-pong loops.
  • Preserving pre-existing dirty working tree changes safely.
  • Tracking regression findings across rounds by stable IDs.
  • Handling provider rate limits and subscription quota resets cleanly.
  • rounds.md alone represents 350+ lines of battle-tested edge cases!

🏗️ The Layered Architecture Pattern

Standardize plumbing; customize domain logic.

  • Commodity Core (Shared Skills):
    Context isolation, review/fix state machine, PR delivery (work, review).
  • Repository Layer (AGENTS.md):
    Repo architecture, test commands, lint rules, local conventions.
  • Preferences Layer (preferences.md):
    Per-role model assignments, and the ## Work worker-round allowance.
  • Domain Leaf Skills:
    Org-specific internal tooling, deployment APIs, telemetry queries.

Slide 9: Shared Skills vs. Every Engineer/Org Forking Their Own

  • Stepping back from AgenticAle specifically: how should teams think about adopting shared skills versus every engineer or org rolling their own?
  • It's tempting to think a review loop is just a 10-line prompt. Then you hit reality: What if the working tree already had uncommitted changes before /work started? What if the fixer fixes Bug A but introduces Bug B? What if the worker tries to delegate to another worker infinitely?
  • Solve orchestration plumbing once in a shared, well-tested skill, and customize at the edges: put your repo rules in AGENTS.md, your model preferences in .agenticale/preferences.md, and write small domain-specific supporting skills for your org's unique tools.
Section 5 • The Frontier Experiment

/autonomous — A Self-Driving Backlog Loop

Attaching /work's strict review primitives to durable on-disk state

📋 Core Loop on Disk

Reuses /work task contracts and strict independent review gates backed by persistent files:

  • Reads next item from BACKLOG.md.
  • Executes implementation & strict review.
  • Refines & grooms remaining backlog items.
  • Writes 2-line ledger entry and exact NEXT state in .agenticale/handoffs/active.md.

⏳ Quota & Cooldown Aware

Built for subscription rate limits and overnight resilience:

  • Detects provider rate-limit windows (e.g. 5-hour rolling limits).
  • Persists cooldown timestamp directly in active.md.
  • Pauses gracefully and resumes cleanly when the subscription window resets.
  • Zero lost progress or chat context exhaustion.

💻 Local Model Friendly

Hybrid cloud & on-device model configuration:

  • Pair fast local models (via Ollama / LM Studio) for routine coding.
  • Point the review role at strong cloud reasoning models.
  • Ideal use case today: Side projects, greenfield prototypes, and overnight mechanical refactors.

Slide 10: /autonomous — A Self-Driving Backlog Loop

  • Before we open up for questions, I want to spend 5 minutes on the most experimental part of the repo: /autonomous mode.
  • Think of /autonomous as asking: "What happens if we take /work's fresh subagent and strict review primitives, and attach them to a durable project backlog on disk?"
  • Instead of keeping state only in the chat session, /autonomous maintains BACKLOG.md and .agenticale/handoffs/active.md. It picks a task, runs worker and strict review rounds, refines the backlog as it learns more about the codebase, and writes a durable checkpoint after every single round.
  • Two features make it especially fun for hobby projects:
  • 1. Subscription window awareness: If you hit a provider quota limit at 2 AM, it records the exact state and cooldown window in the handoff file so it can wait or resume later with zero lost work.
  • 2. Hybrid local/cloud configuration: You can point routine coding roles at local models while keeping a strong cloud model for the reviewer.
  • I wouldn't point /autonomous at a mission-critical production monorepo unattended tomorrow—but as a sandbox for side projects and seeing where long-horizon engineering is headed, it's eye-opening.
